# Autonomous delivery

Runs only when `plan.md` has `Delivery: autonomous`, which the `plan` skill writes only on a `personal` origin. Etienne's "accepted" on the plan, given after the critique closed, was the last approval before the PR, except the escalations below.

Before this file applies, the plan carries a closed critique: an interactive session produces it through "Interactive autonomous plan" in the `plan` skill, a pane through `hand-off-plan plan --auto`.

Claude coordinates. A Claude session that accepted the plan is the coordinator. A Codex session that accepted it runs `~/.claude/skills/plan/scripts/start-delivery` from the change's worktree and stops: the script checks the committed plan, its closed critique and the preflight, then starts a Claude coordinator. Inside herdr that is a pane below (`hand-off-plan.sh deliver <slug>`); outside herdr it is a background session (`claude --bg`), and the script prints how to attach to it and where its report lands. If the script refuses, report its output to Etienne and stop. Codex coordinates only on Etienne's explicit instruction; Codex otherwise stays the plan critic and, only on `Codex review: yes`, the second reviewer.

The coordinator keeps a progress note, `deliver-<slug>.md` in the `herdr` folder of the git common dir, current after every stage: the stage reached, the blockers, the report paths and the next action. A resumed or restarted coordinator reads the progress note first, then `~/.claude/skills/finish/scripts/delivery-evidence status`, then `review.md`, and resumes from the next action. It never repeats a stage whose result is committed and fresh.

Preflight first. Run `~/.claude/skills/plan/scripts/delivery-preflight`, with `--needs database` and `--needs browser` when the agreed proof needs a migration replay or a browser check. The needs follow the rule `delivery-evidence check` enforces at `finish`: a change that touches migrations needs `database`, a change that touches UI paths needs `browser`. Leaving a need out only moves the blocker to the end. On `Blockers:`, stop and report every missing item together in one message, before any costly work. Never turn a missing check into a skip.

1. Run the `implement` stage: `COORDINATOR=<own pane id> ~/.agents/bin/hand-off-plan implement <slug> --auto` (in herdr-app the own id is `$HC_TERMINAL_ID`). Wait for its `Handoff done:` line, then read its report.
2. A `Decision needed:` line in a report is an escalation (below). Settle it before the next step.
3. Run the tests, the linters, Brakeman and Bundler Audit where the repository has them, each through `~/.claude/skills/finish/scripts/delivery-evidence run --kind <tests|lint|audit> --name <name> [--summary <counts>] -- <command>`. The script records the result against the exact content it ran on and never stores the output. It records the command line, and the pull request body publishes it. Never put a secret on the command line: pass it through the environment.
4. Exercise the behaviour as a human would. Record each scenario with `delivery-evidence record --kind <browser|migration|check> --name <name> --status pass|fail --scenario <what you did> --result <what you saw>`, with `--paths` naming what the proof depends on and `--limits` for what it did not cover. Replay a migration only on a scratch copy of a database, never the original.
5. Review. Follow the `review` skill in auto mode. A Codex coordinator uses its read-only Claude CLI backend for the Claude round. A Claude coordinator chooses its pane or `here` backend according to the session. A Codex coordinator works on Etienne's explicit instruction only. Run the Claude round and, only when `plan.md` records `Codex review: yes`, the separate Codex round before it (Codex round first, then the Claude round), transcribing each round and running `commit-review`, then pushing the branch when it exits 0 (`git push -u origin HEAD`). Rounds with open findings stay uncommitted. Fix findings through `code-review`, then run each enabled reviewer again. Repeat until a round of each enabled reviewer leaves no open finding.
6. Before delivering, run `delivery-evidence status`. Any `stale` or `failed` entry, from a fix, a rebase or an uncommitted edit, is rerun and recorded again. Commits that touch only `docs/changes/<slug>/` never make evidence stale. Record the delivered behaviour with `delivery-evidence note --delivered <text>` and each material limitation with `note --limitation <text>`.
7. Once a round of each enabled reviewer leaves no open finding, confirm that `plan.md` is accepted and records `Delivery: autonomous`, because `deliver` removes it. Write the account — behaviour delivered, evidence, check results, review outcome — to `docs/changes/<slug>/deliver.md` and commit that file alone: `git add docs/changes/<slug>/deliver.md`, then commit with the subject `docs: delivery account for <slug>`. `deliver` removes the folder in its own commit, so the account stays in git history. The PR URL and the CI result exist only after `deliver`: they do not go in the account. Then follow `~/.claude/skills/deliver/SKILL.md`. For an autonomous change it refuses on missing, failed or stale evidence, builds the draft PR body from the handover, opens the draft PR and checks the PR head and body afterwards. After `deliver`, follow `~/.claude/skills/finish/SKILL.md` in its auto mode, which runs `ship --no-merge`: it marks the PR ready and waits for green CI. Red CI stops the delivery: report the failed checks and their links.
8. Tell Etienne the behaviour delivered, the PR URL, the CI result and the account path. Never merge: Etienne's `/finish` is the merge approval.

A stage pane started by `hand-off-plan plan` or `hand-off-plan deliver` is still the coordinator: its starting prompt names another pane, but every stage gets this session's own pane id. That other pane receives only the final message, as the single line `Delivery done: docs/changes/<slug>/deliver.md`, sent once the delivery ends; the account path also goes into the report file the starting prompt names, with the PR URL and the CI result.

Escalation: stop and ask Etienne one concrete question when a choice changes the agreed behaviour, a step needs a permission he has not approved, one problem fails three times, or a finding is still disputed after two rounds. A `Decision needed:` line in a stage report is how a pane raises one of these.

Outside herdr, herdr-app and Rex, run the `implement` stage's `here` backend with the `auto` argument in this session instead of a pane.
