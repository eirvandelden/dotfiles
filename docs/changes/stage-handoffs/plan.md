# Plan: every stage after intent runs in a fresh agent pane

From `intent.md` and `spec.md` (2026-09-28; spec revised 2026-09-29). Status: accepted (2026-09-29).

This is a revision of the accepted plan from 2026-09-28 (implemented, review rounds 1–2 closed). It layers on top of that work rather than redoing it: three of the four stage entries in `hand-off-plan.sh`'s table already exist, `implement/SKILL.md`'s `here`/pane split already exists, and `finish/SKILL.md`'s leftover-pane step already exists — none of that is touched again here. What changes: `spec`'s model and direction, `plan`'s permission mode, a new `intent` stage entry, and a new chain-to-next-stage step every accepting stage now takes.

## Files that change

- `herdr/.config/herdr/scripts/hand-off-plan.sh` — the per-stage table gains a `direction` column (`down` for `intent`, `plan`, `implement`; `right` for `spec`, matching `spec.md` §4) and a `next_stage` column (`intent`→`spec`, `spec`→`plan`, `plan`→`implement`, `implement`→none). `spec`'s model changes from `opus` to `sonnet`. `plan`'s `agent start` call drops `--permission-mode plan` entirely — the `case "$stage" in plan) ... esac` special-cased invocation goes away, replaced by the same generic `agent start` call every stage now uses, plus a plan-only prompt sentence: "Write `plan.md` and touch nothing else in this worktree until Etienne says the literal word 'accepted'." A new `intent` table row: model `opus`, ready word `Intent ready:`, role instruction pointing at the intent skill with no upstream artifact (`intent`'s own interview is what creates `intent.md`), pushes after acceptance (same as `spec`/`plan`). Every stage but `implement` gains one more prompt sentence, right before the report/close instructions: "Your coordinator's pane id is `<id>`; the skill's Accept step starts the next stage with `HERDR_PANE_ID` set to that id." The prompt carries no chain command: the skill owns the chain, so a stage pane cannot chain twice, and the skill chains only after its commit and push. If starting the next stage fails, the prompt tells the pane to add one line saying so, and why, to its own report file before sending the report line — so the durable report explains a stalled chain instead of leaving Etienne to notice a missing pane and guess (interrogated 2026-09-29).
- `claude/.claude/skills/intent/SKILL.md` — new "Choosing a backend" section: no argument keeps today's default (interview in the current session); `handoff <slug-or-issue>` resolves the slug or issue the same way step 1 already does, then runs `~/.config/herdr/scripts/hand-off-plan.sh intent <slug>` and stops, exactly like `spec`'s and `plan`'s pane backends do today. §4 Accept is reworded: today's "Nothing else changes state" is wrong once this lands — replaced with "inside herdr (`HERDR_ENV` set), also start the spec stage: `~/.config/herdr/scripts/hand-off-plan.sh spec <slug>`; if that fails, say so and stop there instead of silently leaving it; outside herdr, stop here."
- `claude/.claude/skills/spec/SKILL.md` — "Pane backend" section's model/direction prose updated (Sonnet, splits to the right). Its Accept step commits, pushes, then chains to `plan` with the coordinator's pane id (including the "say so on failure" clause), worded for spec's own next stage.
- `claude/.claude/skills/plan/SKILL.md` — "Pane backend" section drops the "already in plan mode" sentence, replaced with the "write `plan.md`, touch nothing else until accepted" wording (matching the script's own new prompt sentence, so the doc and the script never drift). Step 7 (accept) commits, pushes, then chains to `implement` with the coordinator's pane id (same failure clause).
- `claude/.claude/skills/implement/SKILL.md` — no change. It has no `accepted` status line to flip, so it is outside the chain (`spec.md` §8's third bullet); its existing `here`/pane split from the first round stands as-is.
- `claude/.claude/skills/finish/SKILL.md` — no change; its leftover-stage-pane step from the first round already covers a stage pane of any of the four kinds.
- `docs/changes/ai-native-workflow/habits.md` — habit 1 (Intent) gains a line about the optional `handoff` argument and the auto-chain to spec; habit 2 (Spec)'s "fresh Opus pane" becomes "fresh Sonnet pane to the right"; habit 3 (Plan) drops "already in plan mode," replaced with "told to write `plan.md` and touch nothing else until you accept it." All three note that accepting starts the next stage without a separate command from the coordinator.
- `herdr/.config/herdr/README.md` — the "Worker scripts" paragraph's stage list grows to include `intent`, and gains a clause about per-stage direction and the chain-to-next-stage step.
- `test/herdr_worker_scripts_test.rb` — `hand-off-plan.sh` section extended: a fourth stage (`intent`), the direction column, the dropped plan-mode flag, and the coordinator-id prompt line (no chain command), on top of the existing coverage from the first round. `start-review.sh` section untouched.

## Risks

- **A failed chain call, resolved.** Interrogated 2026-09-29: a failed `hand-off-plan.sh <next-stage> <slug>` call (worktree conflict, `agent start` rejected) is not left silent — the accepting pane adds one line to its own report file saying the chain failed and why, before sending its report line and closing. Etienne finds that reason already written down instead of having to guess from a missing pane. The `here` backend's equivalent (no report file to write into) says so directly in-session instead and stops there.
- **`intent handoff`'s slug must exist before the worktree does.** Unlike `spec`/`plan`/`implement`, where the branch is already fixed by an earlier accepted artifact, `intent handoff <slug-or-issue>` needs a final slug *before* `hand-off-plan.sh` can create the worktree — so `intent/SKILL.md`'s handoff argument handling duplicates step 1's issue-lookup/kebab-casing logic rather than reusing it inside the pane. Accepted as the minimal fix; a shared script for that derivation is out of scope here (nothing else needs it yet).
- **Dropping plan mode loses a tool-level backstop** (`spec.md`'s flagged concern) — the plan pane can now technically edit code before "accepted," restrained only by its own prompt instruction, the same restraint spec's pane already runs on. Not a new risk this plan introduces, just carried forward from the flagged concern; no additional mitigation planned.
- **Test-stub pane ids shift.** The fake `herdr` stub picks a pane id from `--direction down` vs. anything else; `spec` moving to `right` means its stubbed pane id changes from `w1:pV` to `w1:pW` (the same id `review-w1-pw` already uses in a different call — no collision, just worth noting so a future reader isn't surprised two different tests share that literal string).
